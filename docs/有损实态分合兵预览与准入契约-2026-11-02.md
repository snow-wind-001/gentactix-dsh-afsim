# 有损实态分合兵预览与准入契约

本轮实现 K05 的当前实态分配计算与只读入口。它能验证“如何分配现有部队”，尚不能在运行中的战局提交新执行单位。`preview_only=true`、`runtime_admitted=false` 是接口事实；预览成功不得展示为已分兵、已合编或已执行命令。45 场的 270 项完整历史窗口仍未验收。

## 已实现的共同分配规则

`gentactix/formation_conversion.py` 复用现有人员分类、计算分队和历史来源验证器，不执行战斗、不另建状态库。分配依据是**当前投入基数和当前伤损**，不是满编模板。

| 账目／状态 | 细分 | 合并 |
|---|---|---|
| 人员 | 容量约束的整数分配；现有、阵亡、负伤、失踪、被俘、未分类及非战斗减员守恒 | 同分类相加；未知不填成已知零 |
| 分类装备 | 投入、可用、待修、毁损整数守恒；毁伤余量分配一次 | 分项相加，不通过合编修好装备 |
| 五类绝对库存 | 最大余数法完整分配；大库存不受人数上限约束 | 直接相加 |
| 粮弹归一化覆盖 | 保持原覆盖，分配固定根账资源尺度 | 按固定尺度加权；不按当前剩余人数重置 |
| 损耗及保障余量 | 按份额分配，不复制、不清零 | 相加；达到整数的债务在执行契约接通前拒绝 |
| 疲劳、压制、情报陈旧、射击冷却 | 保留当前强度和等待时间 | 取较差状态；防护、工事、信号、置信度不择优恢复 |
| 位置、健康、士气 | 沿用当前状态 | 只接受 10 米控制容差内同地单位；健康和可比士气取较低值 |
| 上一轮回执 | 留在提案 `before` 前史 | 不复制为新实体已经发生的执行或战果 |

归一化覆盖与绝对库存的单位不同，不能直接相加。上述分配是计算估计，不代表逐名人员、逐件武器的历史身份。展开面积暂沿用强度状态；物理执行前仍须通过火力密度和粒度敏感性检测。

历史细分只能使用冻结资料中同阵营、直接隶属且本阶段 `reported_present` 的下级。下级覆盖未证明完整时，必须保留“未分配余部（估计）”；仅有真实番号不能证明该部已到达本战场。合成模式允许明确标注的计算分队名。嵌套细分保留直接父级；部分合并不能恢复成完整父单位的名称。

异地合并、渡运及载荷未交接、未知状态字段、跨根历史改编、达到整数的合并余量债，均明确拒绝，原输入不变。目前合并计算只支持有共同分配父系的候选分队，未宣称任意历史单位可合编。

## DSH 和 HTTP 接点

沿用当前 Cordis 插件、公开工具桥和宿主角色可见性，增加 `preview_force_conversion`，没有重新实现模型工具循环。工具先从现有会话解析命令单位 ID，再读取权威实态；调用方不能提交替代世界、模式或 `commit` 指令。结果每页最多八项，使用世界、命令、组织修订和提案摘要绑定 `view_version`；前态变化须重新读取。

HTTP：`POST /api/sessions/{sid}/force-organization/conversion-preview`。请求须带 `expected_turn`、命令 `revision`、`world_version`，可再约束 `organization_revision`。历史与合成用途由会话决定。接口不持久化提案、不增加执行实体、不调用 `session_store.save`。

示例领域参数（`committed` 必须取本单位当前投入账，不能用现有人数替代）：

```json
{
  "kind": "split",
  "unit_ids": ["已登记命令单位ID"],
  "allocations": [
    {"id": "left", "label": "左翼计算分队", "committed": 4000},
    {"id": "right", "label": "右翼计算分队", "committed": 6000}
  ],
  "assumption": "合成演习估计分配；尚不执行分兵",
  "limit": 1
}
```

历史模式每项改用 `historical_unit_id`，余部为 `null`，不得自行填造下级名称。

## 测试记录与实际边界

新增 27 项回归覆盖人员、装备、库存、余量、嵌套谱系、来源在场、分页修订，以及 HTTP／Native 桥只读行为。初次真实 Native 回合发现两项新模块兼容遗漏：`last_combat_effects` 战果回执和装备 `carried_forward` 来源标记。先补失败回归，再修复；从原已提交 T1 恢复预览，未重复推进或重算战损。测试脚本自身还修正了“所有单位必有 `calculation_unit_id`”的错误假设，该项不记作产品错误。

真实 Native 问答另发现 `afsim_state.operation_context` 未携带 `product_mode`，使合成局的工具误用历史规则。第一次工具拒绝和模型的 `preview_rows=0` 原回答保留；其中模型仍答 `totals_equal=true`，无成功预览支持，不能算验收通过。补齐用途字段并增加真实宿主分发链回归后，复测通过。进一步检查发现 `role_epoch` 也遗漏，重置代次 3 的有效单位 ID 在工具中不可解析；失败回归后补齐，防止重置后身份及世界版本不一致。没有修改用户模型配置。

实际流程使用正常的“冻结历史基础 → 合成派生草稿 → 建局／初始化 → 双方明确命令 → 推进一轮 → 当前实态预览”。全部兵额、保障及部署为软件 QA 估计，未作历史标定。

| 后端 | 实际回合 | 选定单位累计战斗减员 | 预览结果 |
|---|---|---|---|
| 原生 AFSIM | T1／1800 秒；真实运行返回码 0；双方命令已覆盖，未再调用模型规划 | 1339 | 两页守恒；原世界、历史、命令、组织不变 |
| DSH 执行 | T1／1800 秒；真实模型 effects 提案通过宿主验证 | 1106 | 两页守恒；原世界、历史、命令、组织不变 |

两者不是同一个数值解算器，本次不以损耗相等为验收条件。以上两局分类装备投入为零，另建显式非零装备合成局验证实际装备伤损后的分配，不覆盖或改写原两局。建议新 ID 均不在原实体注册表，未冒充已完成物理分兵。

非零装备局 `593ebb19e334` 在 T1 后同样累计减员 1339 人；164 件分类装备保留为 143 件可用、12 件待修、9 件毁损，并保留各类不足一件的毁伤余量。五类投入分别为装甲 80、火炮 24、防空 8、工兵 12、运输 40；这是合成软件测试参数，不能作为万家岭历史武器编制。两个建议分队逐分类整数相加和余量总账均与当时实态相等；10001 发炮弹、4001 发防空弹药、20003 升燃油完整分配。预览前后世界、历史、命令和组织保持一致。该例验证实际有损装备预览，仍未执行分兵或合并。

两局实际 `/chat` 均通过 Native 工具读取两页预览，分别与 8661／8894 名现有、1339／1106 名累计战斗减员核对一致，并答 `runtime_admitted=false`、`executed=false`。原生工具日志的公开结果能独立证明每页一项、同一 `view_version`、账目相等；并非只检查模型说自己调用过。问答分别耗时约 22.55／24.89 秒，不代表总体推演速度提升。两局完整世界、历史、问答、命令和组织经新进程冷恢复一致；DSH 局问答在最终源码进程下完成。

随后对包括非零装备局的全部三局再次重启测试进程：完整检查点一致，两页预览重新计算后的全部字段也与重启前一致，包含提案摘要、分页版本和装备余量。没有从可变预览缓存恢复结果。证据为 `cold-three-review.json`，早先两局恢复记录仍保留。

证据保留在 `.cache/qa/formation-conversion-2026-11-02/`：`afsim/result.json`、`narrative/result.json`、`equipped-afsim/result.json`、`cold-review.json`、`cold-three-review.json`、`native-tool-audit.json` 和两次成功问答 review。第一次问答及各次失败预览保留；两次因源码继续修正而中断的全量运行不计最终通过。全量运行又发现旧工具白名单测试未加入新只读工具，原失败保留为 `native-policy-red.log`；更新精确白名单预期后，该组 25 项复测通过，未改运行时代码。最终完整检查与这次定向复测须分列，不将原失败日志改写为通过。

## 完整检查结果

最终运行 `python verify_all.py`：首轮 137／138 组通过，唯一失败为旧的工具白名单测试。只更新该精确允许列表的预期后，`verify_afsim_backend.py` 整组 25 项复测通过。运行时代码未因该项复测改变。

综合有效结果为 **138 组、1569 项 unittest、零未解决失败、零跳过**；包括上下文退化检查及干跑探针。分组有效耗时合计 852.05 秒，不是单次全量命令的墙钟时间。八份已冻结源码前后不变；白名单回归的单独后续修订另有指纹。68 项受保护配置、原存档和默认资料未变，45 场 270 格完整历史状态仍为 `not_run`。

`final-offline-gate/results.json` 保存首次完整运行的原始 1 组失败，`verify_afsim_backend-remediated.log` 保存 25 项复测；`acceptance-results.json` 列明合并依据，`validation-summary.json` 汇总真实模型、装备实测、冷恢复和明确未完成项。两次早期因源码修正而中断的运行不计成绩。没有声称一次全量命令零失败，也没有以此验收完整历史或实际物理分合兵。

## 后续执行顺序与检测要求

### K05-A：唯一根账与有效叶子集合

在现有世界内登记版本化转换事务和互斥执行身份。原历史初态仍冻结，不修改 `mission.definition` 或初始化满编模板来绕过校验。根账必须同时约束人员投入、分类装备投入、固定资源尺度及旧新身份的完整覆盖，拒绝复制分队后改 ID、重放旧事务、重复退役或遗漏余部。当前仅有计数谱系，不能代替唯一所有权证明。

宿主应从原世界重新计算候选，核对世界／命令／组织修订后提交；持久化失败保持原世界和队列。为 `missions.validate`、`historical_operations.validate_identity`、`formation_parts.validate` 建立统一受审计的有效叶子视图，不能分别放松冻结身份约束。验证带伤损、非零装备、多个初始分队、嵌套分合、两边相同名称和冷恢复；整数账零误差，根资源尺度不变。

### K05-B：指挥、持续任务和目标接续

明确旧命令身份到新叶子的映射、优先级及取消规则，接续 `force_organization`、持续任务、人工接管和 `unit_participation`。旧任务的执行次数和已完成依赖不能清零、复制或二次释放。异地合编仍各自机动，不能用组织关系改变物理坐标。

目标中的原历史单位选择器须映射到其互斥后代，保持原投入分母、累计损失及达成里程碑；不能将一个师拆成数个分队多领奖，或重建目标图来取消已完成结果。检验交战中细分、任务中暂不支持的负例、分途机动后集结、阶段转换、真正取消与人工待命差异，以及完整冷恢复。

### K05-C：两种执行后端与观察

接续 `campaign`、补给绑定、原生场景平台及 DSH `unit_updates` 的有效身份。AFSIM 在新回合只编译当前活动叶子，旧实体进入历史；DSH 只能读取、提交当前有效身份。各类库存、损耗余量、冷却与回执所有权必须相同。显式规定跨轮工具分页失效及轨迹查询的身份谱系，保持 DSH 原生会话和压缩接续，不把完整世界塞回提示词。

先检验同总时长待命、射击、运补的 1／2／4 分队对照，查找单位数导致的额外弹药、射速、补给和目标收益。再做两后端真实回合、旧 ID 拒绝、新 ID 可控、重放及冷恢复；无同范围历史证据的结果仍为未标定。

### K05-D：界面事务与实操验收

上述契约通过后才开放“分兵／合编”执行按钮。单位选择、地图集结点与自然语言意图沿用当前控制链路；界面展示前后人员／装备／库存、来源／估计、余部、未支持项和命令任务影响。实际提交须显示成功或具体拒绝原因，超时不能先显示成功。测试窄屏、重叠单位选择、并发过期、持久化失败、撤销／重试和重启恢复，再进行历史单场长窗口验收。

本轮未修改受保护配置、原存档和默认历史资料；未上传、打包或替换安装程序。运行中物理分合、在途交接、跨根历史改编以及完整历史有效性继续列为未完成。
