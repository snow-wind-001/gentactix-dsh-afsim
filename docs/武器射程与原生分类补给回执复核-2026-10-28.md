# 武器射程与原生分类补给回执复核

本轮继续推进AFSIM后台计算、DSH控制与观察、现有Vue地图与指挥界面的同一目标。未发布、未打包、未替换安装程序或上传GitHub。完整历史业务验收仍为0/45，不以本轮软件检查替代逐场验收。

## 已确认的问题

1. 原生炮击使用12公里射程，交战示意却按单位800米自卫直射范围生成960米图形。单位名与实际炮击都存在，显示仍不能准确表达所用武器。
2. DSH观察统一列出炮击、防空射程，即使单位没有配发这些装备；间瞄最小射程没有与动作一并提供。
3. 地图用经纬度差直接计算方位，在高纬度会偏转。Python与Vue虽相互一致，也可能一起错。
4. 模型把事件的回合内发生时点写成持续时间；库存变化过大时，有限摘要又只保留“formation变化”，丢掉关键收支数字。
5. 轮末实际收到24发炮弹，但旧回执只有到货总吨位，模型曾把24发解释为未消耗余量。这不是通过增加提示词即可证明正确的结果，需补原生证据。

## 数据契约与实现

`gentactix.combined_arms.weapon_limits`只解析已有声明，复用于命令能力、输入校验、AFSIM直射输入和观察；没有新增战斗执行器。`weapon_limits_m`分列各动作的最小、最大射程，`actions`仍决定当前资源是否支持行动。未配发的炮击、防空能力不再出现；已配发但损坏或缺弹时保留名义范围，不能据此声称武器可用。

`weapon_warnings`提示旧炮兵自卫范围疑点，旧冻结输入和损失保持原样。上一轮的新历史配置拦截仍有效。本次还检查45个合成种子及各自配置派生，共540项单位输入：默认直射与间瞄参数已经分开，不为未确认的问题重写整个火力模型。这项检查不等于45场历史部署已正确。

Vue指挥面板随所选动作显示范围；地图补出炮兵最小射程边界。实际交战示意按`weapon_action`选择射程，仍明确标注1.2倍显示系数、非杀伤半径、未计算地形通视。两套渲染器升级为`sector-v4`，采用球面初始方位角和终点公式；不改变后台冻结几何/战损参数，也不宣称旧平面近似内核已经整体替换。

原生WSF在既有分类物资转移处增加`GTXCSUPPLY`记录，回传燃油、备件、施工材料、炮弹、防空弹药五项实际到货量，契约版本为1。宿主检查缺项、重复、负数、单位收支和仓库出库一致性，再把`received_*`写入本轮执行回执。该改动增加观测，不在Python中计算到货。旧回执缺字段时保留缺载，不能填成已知零到货。

观察同时明确：事件`seconds`为回合内发生时点，`active_fire_s`为有效火力时长，`delay_s`为计划通信等待，`received_*`为轮末到货。大变更仍压缩，但为人员和库存保留限定字段的前后数值；不复制长来源和完整历史。问答中的“程序事实”与右侧保障页直接列出分类到货，模型解读另行显示。

## 真实验证

验收使用独立加密QA配置、high思考强度、65536输出预算；实际4份模型请求头均符合此配置，调用既有原生`get_afsim_observation`、`get_afsim_changes`、`evaluate_action`。没有修改DSH全局配置、引入另一套智能体运行时或增加步骤预算。

三单位使用既有真实ID，但人数、炮兵聚合、部署与射程是明确QA参数，尤其第31师在此被设为炮兵聚合，仅用于武器契约测试，不能解释为该师真实兵种或完整徐州会战。目标约4.4公里：800米`fire`命令在执行前被拒绝，战局不变；合法炮击可以入队，入队本身不执行。随后由真实DSH为未人工覆盖的红方选择`bombard`，蓝方人工待命，AFSIM实际执行。

实际结果为8个周期、960秒有效火力、发射120发炮弹；30分钟回合在1800秒结束。地图实际生成炮击图形与12000米依据，不再按800米直射范围绘制。只读问答保持主战局不变。另导入自己先前的九单位QA旧局，8000米旧范围、人员损失均未改写，界面显示疑点。

补齐分类回执后，用相同参数和动作再次原生运行，三单位的人员、装备和库存分别与前次结果相同，火力周期与停止原因也相同。新回执与模型正确核对：

```text
炮弹：轮初120 − 实际发射120 + 轮末到货24 = 最终库存24发
弹药工作量：轮初80 − 消耗8 + 到货2 = 最终库存74
```

先因耗尽停止射击、后在轮末收到24发，不能用最终非零库存反推射击过程中一直有弹。实际第三次问答已正确说明这一点，并区分155.928秒发生时点、960秒火力时长和1800秒回合历时；前两份错误/缺证据解释仍保留，未覆盖成成功记录。自由文本仍需核对，不能由这一次正确回答推及全部问答。
