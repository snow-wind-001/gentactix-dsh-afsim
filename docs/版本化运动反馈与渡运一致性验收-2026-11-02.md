# 版本化运动反馈与渡运一致性验收

本增量处理DSH移动后疲劳不变、实际位移未扣通信／压制等等待的问题。新增显式`movement-feedback-1`，保留原生名义速度，并在命令与结果准入中分别检查有效陆地预算、运输过程和疲劳。最终完整离线**153组／1783项unittest、0失败／0跳过**通过，分组耗时合计972.68秒。完整22单位从真实前端完成一小时DSH推进与同命令AFSIM对照，全部疲劳一致，最大位置差约1.55厘米；两局完整冷恢复一致。**尚未通过长期完整会战、补给策略一致性、全部解释或历史标定。** 旧默认选择、冻结资料与原失败存档不迁移，未上传或替换安装版。

## 计算规则与执行边界

- `missions.move_budget`继续提供原生速度所需的名义预算，避免速度和暂停重复折减。普通陆地命令另扣既有通信延迟、疲劳、压制、可用兵力及燃油约束；道路按登记目的地核对，不宣称具有DEM或视线遮挡。
- 轮末疲劳由实际陆地公里与`fatigue_move_gain`决定；休整使用既有恢复系数，启用时间保障时按秒数缩放。缺粮造成的疲劳是下限，不再次相加。其他动作不能任意重置疲劳。
- 桥梁／通路命令仍是排队路线请求，结果联合核对接近、排队服务与走完整通路的时间；名义目标不表示本轮已经抵达。
- 舟艇水程独立于乘员自主陆地路程。乘艇不收地面行驶油或行军疲劳，登岸后才计算地面段；原有船速、容量、装卸和事件回执仍须独立通过。
- DSH提交状态变化，宿主只校验和拒收。AFSIM继续实际执行，新增`GTXMOVEMENT`回执与原坐标／通路互核，没有另建Python战斗执行器或世界状态库。

通信延迟和疲劳的原生`GtxRound`采用就近偶数舍入。新增失败回归证实`2.5`秒原Python得到`3`、原生得到`2`；显式新模型现对齐，未启用的新旧存档仍保留原延迟规则。

## 版本与正常入口

新增可选择的万家岭窗口`WJL-oct6-10@1.5.0`，绑定**原AJ07史料1.4.0**；22单位身份、人员装备先验、部署和库存与原窗口一致，只增加运动反馈计算配置与说明。不把规则版本冒充新史实，不提高旧先验的历史可信度。

沿用DSH原生想定插件、分片工具、最终校验及运行入口。前端增加默认不勾选的运动反馈生成要求；显式要求时，配置缺少该模型不能启动。新窗口的既定运动配置也不能被生成结果悄悄丢弃。阶段续接保存该规则及累积疲劳，拒绝中途移除或换算。

## 先失败再修复

新增`verify_movement_feedback.py`覆盖旧定义不变、错误配置、有效机动、持续移动、错误疲劳拒收且不改世界、休整、偶数舍入、兵力／压制／待入场、燃油、缺粮下限、原生回执完整性及乘艇地面段。追加延迟渡河回归后，相关入口和阶段续接共69项通过。

补测还发现：耗尽地面燃油的车辆分队已在岸边时，被零陆地预算挡住，无法发出纯乘艇请求。现仅在启用新规则、已登记舟艇路线且所需陆地距离为零的情况下允许；不放开自主地面行军。实际AFSIM完成三轮渡运并登岸，地面燃油维持零。

实际渡船另出现约0.203米的船／乘员轮末回执差：原生一秒周期带错峰时刻，乘员位置少同步了轮末不足一秒。新增模型在轮末采样前调用既有`GtxFerrySync`，位置与路程校验通过；原3毫米路程互核容差没有放宽。原失败文件保留。

进一步实际测试发现，已在入口的单位可能在零时刻登记排队，再等待通信／疲劳延迟后开始服务。把`entered`误作开始服务会拒收合法原生过程。现区分“原本在岸边”和“本轮行军接近”，仍核对等待、实际服务及行军的合计时间；提前到达的非零接近路径仍拒收。首次全仓检查为此中止留档，修复后重新冻结源码并从头运行门禁，不将中止批次计为通过。
